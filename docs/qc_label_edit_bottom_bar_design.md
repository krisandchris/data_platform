# 标注修改模式底栏与修改说明设计

日期：2026-05-17

## 1. 设计结论

如果样本审阅界面的定位只是给标注人员修改标签，而不是给质检人员做最终裁决，那么底栏不应再使用 `vote note`、`通过`、`驳回` 这套质检裁决语义。

推荐改为：

- `vote note` -> `修改说明` / `change_note`
- `通过`、`驳回`、`人工精标` -> 移除
- 保留或新增：`校验修改`、`保存草稿`、`提交修改`、`跳过样本`

底栏的职责从“给样本下最终结论”调整为“提交本次标签修改事务”。

## 2. `vote note` 关联的原有逻辑

在质检裁决语义下，`vote note` 通常关联这些逻辑：

| 逻辑 | 作用 | 是否保留 |
| --- | --- | --- |
| 裁决依据 | 解释为什么通过、驳回、需人工处理 | 不保留原语义 |
| Pass/Fail 前置校验 | 没有 note 时阻止提交裁决 | 改为修改提交校验 |
| 审计记录 | 记录审核员对本样本的判断理由 | 保留，但改为修改说明 |
| Patch 保存 | 跟随 patch 一起保存，解释改动原因 | 保留 |
| 复核回放 | 后续复核人查看为什么做出该裁决 | 保留，但回放内容是“为什么改这些字段” |

因此它不应该完全删除，而应该降级并改名为 `change_note`。

## 3. 标注修改模式的底栏目标

底栏只处理“本次标签修改任务”的状态，不再表达样本质量裁决。

底栏需要回答四个问题：

1. 当前是否有未保存修改。
2. 当前修改是否合法。
3. 标注人员为什么做了这些修改。
4. 本样本修改是保存为草稿，还是提交完成。

## 4. 推荐底栏布局

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 修改说明                                                                    │
│ [说明本次修改原因，例如：修正 R1 bbox，删除 R3 作为候选证据。]              │
│                                                                            │
│ 已修改 5 项 · 校验通过 · 已保存草稿 21:38        [跳过样本] [校验修改] [保存草稿] [提交修改] │
└────────────────────────────────────────────────────────────────────────────┘
```

布局规则：

- 底栏仍然横跨整个浏览器底部。
- 左侧为 `修改说明` textarea，占主要宽度。
- 右侧为状态摘要和动作按钮。
- 不再出现 `通过`、`驳回`、`人工精标`。
- `提交修改` 是主按钮。
- `保存草稿` 是次按钮。
- `校验修改` 是显式校验入口，也可在提交前自动执行。
- `跳过样本` 是弱按钮，不应该抢占主操作。

## 5. 按钮语义

| 按钮 | 作用 | 是否写入 patch | 是否离开当前样本 |
| --- | --- | --- | --- |
| `跳过样本` | 当前不处理，返回队列或进入下一条 | 否，除非有已保存草稿 | 是 |
| `校验修改` | 运行字段合法性、引用完整性、bbox 合法性检查 | 否 | 否 |
| `保存草稿` | 保存当前 `reviewDraft` patch | 是 | 否 |
| `提交修改` | 校验通过后保存 patch，并将样本标记为已完成标注修改 | 是 | 可配置，默认进入下一条 |

## 6. `修改说明` 必填规则

不建议始终强制填写。应按修改风险分层：

| 场景 | 是否必填 | 原因 |
| --- | --- | --- |
| 没有任何字段修改 | 不可提交，说明禁用或只读 | 无 patch 不应提交 |
| 只改低风险字段，如文本描述、开放标签补充 | 可选 | 改动可由 patch diff 自解释 |
| 修改闭集标签，如 `violation_category`、`relation`、`sample_category` | 必填 | 影响训练标签和统计口径 |
| 修改 `bbox` | 必填 | 空间标注变化需要人工依据 |
| 删除 Relation 或删除 Candidate 证据 | 必填 | 影响证据链完整性 |
| 新增人工 Candidate | 必填 | 需要说明新增依据 |
| 提交前存在警告但允许提交 | 必填 | 需要记录人工接受风险的原因 |

## 7. 底栏状态摘要

底栏应显示一个紧凑状态摘要，不再放大成单独卡片。

建议显示：

- `已修改 N 项`
- `未保存` / `已保存草稿 HH:mm`
- `校验通过` / `校验失败 N 项` / `有警告 N 项`
- `配置版本 urban_violation_labels_v1`

状态摘要示例：

```text
已修改 5 项 · 校验通过 · 已保存草稿 21:38 · config v1
```

如果校验失败：

```text
已修改 5 项 · 校验失败 2 项 · 请修正后提交
```

## 8. 提交流程

```text
标注人员修改字段
  -> reviewDraft 产生 dirty fields
  -> buildPatch 生成差异
  -> 校验修改
      -> active label config 存在
      -> closed enum 值合法
      -> open tags 格式合法
      -> bbox 仍为 0-1000 且 x1 < x2, y1 < y2
      -> Candidate 证据 Relation 引用有效
      -> required fields 不为空
      -> 高风险修改满足 change_note 必填
  -> 保存草稿
  -> 提交修改
      -> 保存 patch
      -> 标记样本状态为 annotation_modified / annotation_submitted
      -> 写入 audit log
      -> 默认跳到下一条
```

## 9. Patch 字段建议

提交 payload 中不再使用 `review_decision`，而是使用标注任务状态：

```json
{
  "sample_id": "000142_0_1762483003246",
  "task_mode": "label_edit",
  "label_config_id": "label-config-20260517-001",
  "label_config_version": "urban_violation_labels_v1",
  "operations": [],
  "change_note": "修正 R1 bbox，删除 R3 作为候选证据。",
  "submit_action": "submit_changes",
  "task_status": "annotation_submitted"
}
```

草稿保存：

```json
{
  "submit_action": "save_draft",
  "task_status": "annotation_draft",
  "change_note": "先修正 bbox，候选证据待复查。"
}
```

## 10. 与当前预览稿的调整

当前 `docs/qc_step_review_field_layout_preview.html` 应调整为：

- 底栏标题从 `vote note` 改为 `修改说明`。
- 底栏 aria-label 从 `质检裁决底栏` 改为 `标注修改底栏`。
- 按钮改为：`跳过样本`、`校验修改`、`保存草稿`、`提交修改`。
- 删除 `通过`、`需修改`、`驳回`、`人工精标`。
- 状态 chip 改为 `已修改 5 项`、`校验通过`、`草稿已保存`。

## 11. 验收标准

- 底栏不再出现质检裁决按钮。
- `修改说明` 与 patch/audit 绑定，而不是与 pass/fail 投票绑定。
- `提交修改` 前必须执行字段校验。
- 高风险修改必须填写 `修改说明`。
- 没有 active label config 时，底栏只能保存查看状态，不能提交修改。
- 没有任何 dirty fields 时，`保存草稿` 和 `提交修改` 禁用。
- 提交后状态进入标注修改完成队列，而不是质检通过/驳回队列。
